## 1. The hole in the story (bigger than code)

**Mandate in your app ≠ mandate on a rail.**

What you store is a **spending policy** (caps, categories). What NPCI/RBI/AP2 mean by mandate is a **pre-authorized instrument** (token / e-mandate) created with human AFA, later debited under rules.

| Layer | What you have | What a reviewer hears |
|--------|----------------|------------------------|
| Create | PIN `1234` overlay | Fake AFA |
| Bound | JS if-statements on a Zustand object | Real idea, weak enforcement |
| Pay | Razorpay **Checkout** (human types card) | Customer-present payment |
| Agent | Did not move money | Human did |

So “AI buyer end-to-end” is **overclaimed**. After notify, a **person** finishes Checkout. That is closer to “agent prepares a gated cart, human pays.” That is a **valid, honest** demo. It is **not** agent-to-merchant autopay.

**What to change (pick one, write it in README):**

- **A (recommended for a weekend):** Keep Checkout. Pitch: *“Agent plans and gates; execution is hosted Checkout because test-mode silent debit is not a real Indian rail. Notify→window is the gate.”*  
- **B (stronger if you have time):** After Checkout once, save Razorpay customer + token; later attempts charge the token **without** opening Checkout (still notify-window first). That is the only path that looks like an agent debit.

Do not mix A and B in the pitch.

## 2. The “agent” is a keyword matcher + cheapest SKU

[`parse-intent.ts`](src/lib/safebuy/parse-intent.ts) and [`plan.ts`](src/lib/safebuy/plan.ts) are the brain. They are dummy in ways judges will feel if they type anything other than the canned line.

**Parser**

- `"1 kg"` becomes **item count = 1**, not **1 kilogram**. `"buy 5 kg rice"` can mean five 5 kg bags (25 kg). Pack size and quantity are collapsed.  
- `"under ₹150"` is regex; `"around 200"` / `"max 2 hundred"` miss.  
- Category is synonym lists (`rice` → grains). No SKU-level intent (`basmati` is not a field on `StructuredIntent`).  
- Grok parser exists and is **not on the Buy path**.

**Planner**

- Sort by price, take ≤2 lines, stop after one category.  
- `"buy basmati"` works only because the **name string** contains `basmati`. Guardrail never checks that (next section).  
- Empty cart = silent “no match.” No clarifying question (“1 kg pack or 5 kg bag?”).  
- “Cheapest” is not “best.” For groceries that is OK; for a pitch called *agent* it looks cheap.

**What to change (small, high leverage)**

Extend `StructuredIntent`:

```ts
packTokens: string[]        // ["basmati"] 
excludeTokens: string[]     // ["chocolate"]
qty: number | null          // number of packs
packSizeHint: string | null // "1kg"
```

Planner: filter names/brands by `packTokens`. If 0 or >3 candidates, **ask one question** instead of guessing. That single ask-back is more “agent” than another LLM call.

Keep deterministic parse as fallback. Put Grok behind coerce → **same schema**.

## 3. Guardrail does not catch the real agentic failure

We already said lab-inject chocolate. The **honest** failure is:

> User said basmati. Agent picks atta. Both `grains`. Price under cap. **Guardrail passes.**

[`guardrail.ts`](src/lib/safebuy/guardrail.ts) checks mandate + **categories/brands/qty/price**. It does **not** check name/SKU vs instruction tokens. Planner has a weak token check; the safety layer does not repeat it. If planner is wrong, safety agrees.

Lab mismatch is **staged** (forced Cadbury). A reviewer who types `buy basmati` and then looks at guardrail source will see it cannot fail same-category substitution.

**What to change**

Guardrail step (deterministic):

- `packTokens` must all appear in `name|brand|sku` (normalized).  
- `excludeTokens` must appear in none.  
- Optional: price within X% of remaining / instruction cap (you already discussed this).

Then the chocolate SKU is unnecessary as a special case; it fails `packTokens=["basmati"]`.

Keep the lab inject as a **demo button** that *uses the same guardrail*, not a fake cart the planner would never produce… or keep the inject but also show a natural miss.

## 4. Notify window is a countdown, not a control plane

It is labelled synthetic — good. Still dummy as a **gate**:

- 5s is too short to read SKU + amount + abort on mobile.  
- Abort exists; there is no “hold / extend.”  
- It does not create a durable **pre-debit record** (notice id, amount, merchant, deadline) that the execute step **must** reference. Execute just happens because a timer hit 0.

**What to change**

Make notify a **record**, not a CSS bar:

```
PreDebitNotice { id, attemptId, amountPaise, skus[], issuedAt, executeAfter, status }
execute allowed iff notice.status==issued && now>=executeAfter && not aborted
```

Audit `notify.id` on the Order notes. Then the gate is data, not `setInterval`. Stretch 8–12s or require an explicit “Proceed after notice” **plus** min dwell (so it is not skippable in 50ms). Spec said notify then execute; a skippable overlay is weaker than a notice object.

## Day 2 — `pending` + Fetch + `applyConfirm`

**Goal:** Handler is **not** paid. `captured` is paid.

### Data

On `PurchaseAttempt` add:

```
razorpaySignature: string | null
razorpayStatus: none | created | pending | captured | failed | unknown
confirmSource: none | fetch | webhook
chargeAttempts: number
```

### `applyConfirm({ attemptId, paymentId, orderId, source, amountPaise })`

Preconditions (all or reject):

- attempt exists  
- not already confirmed for this `paymentId` (idempotent map)  
- `amountPaise === cart.totalPaise`  
- `orderId === attempt.razorpayOrderId`  
- mandate remaining ≥ amount **or** in-flight revoke path (Day 8)

Then:

- remainingPaise -= , spentPaise +=  
- phase `confirmed`  
- audit `razorpay.confirmed` { source, paymentId, remaining }

### Handler (Checkout)

```
onSuccess(order_id, payment_id, signature):
  audit razorpay.handler_received   // NOT confirmed
  phase = pending
  store ids
  startReconcile(attemptId, paymentId)
onDismiss:
  failClosed("checkout_dismissed")
  do not assume unpaid (Day 4 late webhook)
```

### `startReconcile`

```
for i in 0..5, wait 2s (disclose: demo poll, not UPI SLA):
  GET /v1/payments/:id     // existing fetchRazorpayPayment — CALL IT
  captured | authorized → applyConfirm(source=fetch)
  failed | cancelled    → failClosed, no retry yet (retry Day 5)
timeout → failClosed("poll_timeout"); flag wait_webhook=true
```

### HMAC Checkout signature (server)

```
message = `${orderId}|${paymentId}`
hmac_sha256(message, KEY_SECRET) hex vs razorpay_signature
timingSafeEqual
fail → failClosed("bad_signature"); do not Fetch-as-success
```

### Acceptance

- Network: GET payment after handler.  
- Mandate remaining changes **only after** `captured`.  
- Tampered payment_id does not confirm.
